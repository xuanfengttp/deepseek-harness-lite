① 前缀匹配原理

[A][B][C][D][E] ↑ 命中（复用KV） ↑ miss（重算）

API 逐 token 比对前缀，一致则复用，否则重算。追加尾部只 miss 新增；插入中间则打断插入点之后的全部缓存。

② 首选策略：Append-Only

动态内容（memory/skill/todo）如何注入而不破坏缓存？

答案：全部追加在消息尾部。

[sys][tools][user1][asst1][memory_result] 前缀全命中 只 miss 新增
动态内容注入方式缓存
Memory recalltool result 追加✅
Todo guidanceuser msg 追加✅
Workflow 指令user msg 追加✅
原则：动态内容一律追加尾部，不插入中间，不修改已有。压缩是唯一的重排窗口。

③ 压缩：唯一重排时机

正常: [sys][tools][user1][asst1][user2] miss 最后一轮
[sys][tools][Summary][recent] 前缀仍命中 新内容 miss →恢复append

Summary 放头部，之后追加不破坏其缓存。不在压缩前重排：被移动消息马上要压缩掉，重排代价无回收窗口。

④ 固定位置插入的代价

有些场景必须把内容插在固定位置（如 system 后插设备状态），与 append 对比？

Append 尾部追加

[sys][tools][user1][asst1][memory]

前缀全命中，只 miss 新增部分。命中率随对话持续爬升。

固定位置插入

[sys][memory][user1][asst1]

插入点之后全部 miss。即使内容格式固定，只要内容变化就打断缓存。已有对话缓存全部失效。

场景Append固定插入
首轮命中率60-80%~0%
第二轮命中率85-99%取决于插入位置
每次新内容只 miss 新增miss 插入点后全部

⑤ 哪些场景被迫固定插入

场景是否可 append说明
Memory recall✅ 可追加通过工具调用，结果天然在尾部
Skill 切换⚠️ 改 systempersona 变化，后缀失效（低频）
设备状态注入❌ 需固定位置必须在 system 后、消息前，否则语义不对
会话恢复 context❌ 需固定位置历史 context 需在对话前
结论：能用 append 的都用 append。被迫固定插入的场景，需评估缓存损失 → 下一节 Block 对齐能否缓解。

⑥ Block 对齐原理

固定插入不可避免时，能否减少缓存损失？

Block 是 prefix matching 的最小粒度。一个 block 内 token 序列完全一致才复用，否则整个 block miss。

未对齐: blk0blk1blk2blk3 [identity+rules | tools |persona|custom] ↑ section 跨 block 边界 对齐后: blk0blk1blk2blk3blk4 [identity+rules ] [tools] [persona] [custom] ↑ section 边界 = block 边界

对齐后：persona 变化只 miss blk3+blk4，blk0+blk1+blk2 独立复用。未对齐：persona 变化可能连带 blk2 也 miss（因为 persona 跨了 blk2 的尾部）。

⑦ 自部署可行，但当前不做

  • 自部署 → 同款分词器 + block_size 已知 → 技术可行
  • 边界浪费 ≤ 15 token（block_size-1），占 system prompt ~5%
  • 只在 section 变化时触发浪费，append-only 运行中无浪费
  • 需引入分词器依赖 + 运行时 tokenize + 动态填充
储备方案：三层设计已达 85-99%，5% 边际收益不够。被迫固定插入场景增多或命中率瓶颈出现时再启用。配置项已预留 cache.align_blocks。
