KV Cache 复用设计 — dsh-lite 上下文编排

原理：前缀匹配

[A][B][C][D][E][F] ↑ 命中（复用） ↑ miss（重算）

追加在尾部 → 只 miss 新增部分
插入在中间 → 插入点之后全部 miss

三层优化

  • ① 分层排序 — system prompt 固定内容在前，动态在后
  • ② 启动预热 — 发最小请求提前缓存 system + tools 前缀
  • ③ 压缩保前缀 — Summary 放头部，system + tools 缓存不失效
identityrulestoolspersonacustom 永不变 半固定 动态

动态内容：Append-Only

内容注入方式缓存
Memory recalltool result 追加尾部✅ 不破坏
Todo guidanceuser msg 追加尾部✅ 不破坏
Skill 切换改 system persona⚠️ 后缀失效
插入中间插入历史之间❌ 打断

追加策略 + 压缩重排

正常运行（两次压缩之间）— Append-Only：

请求2: [sys][tools][user1][asst1][tool1][asst2] miss 只有最后一轮

压缩时—唯一的重排窗口：

[sys][tools][Summary][userN][asstN] 前缀仍命中 新内容 miss，之后恢复 append

为什么不在压缩前重排？ 被移动的消息马上就要被压缩掉了，重排的缓存代价没有回收窗口。

分块协调：为什么不耦合

  • 需知道模型 tokenizer → 破坏 OpenAI 兼容抽象
  • Block 大小是部署端配置，API 不暴露
  • 边际收益低：主要收益来自前缀稳定（已实现）
替代：Trust the API — API 内部已做 block-level matching，agent 只需保证前缀稳定，通过 prompt_cache_hit_tokens 观察命中率。
