① 前缀匹配原理

[A][B][C][D][E] ↑ 命中 ↑ miss

API 逐 token 比对前缀，一致则复用 KV，否则重算。

追加尾部→只 miss 新增；插入中间→打断后缀。

② 固定在前，动态在后

identityrulestoolspersonacustom 永不变 半固定 动态

改 persona/custom 只失效后缀，identity+rules+tools 缓存不受影响。

③ 启动预热

  • 启动时发最小请求（max_tokens=1），提前缓存 system+tools 前缀
  • Fire-and-forget，错误不阻断启动

④ 动态内容：只追加，不插入

运行中 memory/skill/todo 动态注入，如何不打断前缀？
[sys][tools][user1][asst1][MEMORY][asst2] ↑ 插中间：后续全 miss
动态内容注入方式缓存
Memory recalltool result 追加尾部✅
Todo guidanceuser msg 追加尾部✅
Skill 切换改 system persona⚠️ 后缀
插入中间历史消息之间❌

⑤ 压缩：唯一的重排窗口

持续追加会超窗口，何时重排？
正常: [sys][tools][user1][asst1][user2] miss 只有最后一轮
[sys][tools][Summary][userN][asstN] 前缀仍命中 新内容 miss →之后恢复 append

Summary 放头部：之后追加不破坏 Summary 缓存。不在压缩前重排：被移动消息马上要压缩掉，重排代价无回收窗口。

⑥ Block 对齐：可行但储备

自部署可用同款分词器对齐 block 边界，做不做？

技术上可行（自部署分词器+block_size 已知），但：

  • 边界处最多浪费 15 token（block_size-1），占 system prompt 的 ~5%
  • 只有后续 section 变化时才触发浪费 — append-only 运行中无浪费
  • 需引入分词器依赖 + 运行时 tokenize + 动态填充
当前不做：三层设计已达 85-99% 命中率，5% 边际收益不够。作为储备方案，命中率瓶颈时再启用。
