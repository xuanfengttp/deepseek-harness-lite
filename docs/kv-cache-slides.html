KV Cache 复用设计

DeepSeek Harness Lite · 上下文编排与缓存命中率优化

核心问题

DeepSeek API 的 KV cache 是前缀匹配的 — 请求的前 N 个 token 与上次一致即可复用，不重新计算。

命中率越高 → TTFT 越低 → token 费用越省。

黄金法则：任何在中间插入或修改内容的操作，都会使其后所有 token 变成 cache miss。
02 / 08

前缀匹配原理

[A][B][C][D][E][F][G] ← 上次请求到这里 [A][B][C][D][E][F][G][H][I] ↑ 命中（复用） ↑ miss（重算）

关键推论

  • 追加在尾部 → 只 miss 新增部分，前缀全命中
  • 插入在中间 → 插入点之后全部 miss
  • 修改已有内容 → 修改点之后全部 miss
策略：固定内容放前面，动态内容放后面，新增内容追加在尾部。
03 / 08

三层缓存优化

① System Prompt 分层排序

identity(-100)rules(-90)tools(-80)persona(0)custom(10) ← 永不变，缓存价值最高 ← 动态，改了只 invalidate 后缀

② 启动预热

  • 进程启动时发最小请求（max_tokens=1, think=off），让 API 提前缓存 system + tools 前缀
  • Fire-and-forget，错误不阻断

③ 压缩保持前缀

  • Summary 放消息头部（system + tools 之后），前缀仍命中
  • Summary 请求用独立上下文，不膨胀被摘要的对话
04 / 08

问题一：动态内容打断前缀

危险场景

[system][tools][user1][asst1][MEMORY注入][asst2][tool2][asst3] ↑ 从这里开始全部 miss

设计原则：Append-Only

动态内容注入方式缓存影响
Memory recall工具调用 → tool result 追加尾部✅ 不破坏前缀
Todo guidanceuser message 追加尾部✅ 不破坏前缀
Skill 切换改 system prompt persona⚠️ invalidate persona 后缀
插入 memory 到中间插入历史消息之间❌ 打断后缀
原则：所有动态内容一律追加在尾部。不插入中间，不修改已有消息。
05 / 08

问题二：分块协调

思路

部署端 KV cache 按 block 管理（如 16 token/block）。如果 agent 知道分词器和 block 大小，可让 section 边界对齐 block 边界。

为什么不做

问题说明
分词器依赖需知道模型 tokenizer，破坏 OpenAI 兼容抽象
Block 大小不透明部署端配置，API 不暴露
边际收益低主要收益来自前缀稳定（已实现），对齐只省边界几个 token
维护成本高多模型、版本变化都需同步
替代策略：Trust the API — API 内部已做 block-level matching，agent 只需保证前缀稳定。通过 prompt_cache_hit_tokens 观察实际命中率。
06 / 08

问题三：追加优先 + 压缩重排

正常运行（两次压缩之间）— Append-Only

请求1: [sys][tools][user1] miss 只有 user1 请求2: [sys][tools][user1][asst1][tool1][asst2] miss 只有最后一轮 请求3: [sys][tools][user1][asst1][tool1][asst2][user2] miss 只有 user2

压缩时 — 唯一的重排窗口

[sys][tools][Summary][userN-1][asstN-1][userN] 前缀仍命中 新内容 miss 保留最近消息
Summary 放头部（system 之后），最近消息在尾部 → 追加新消息不破坏 Summary 缓存，且语义正确（摘要是背景，最近对话是主线）。

实际命中率

数据来自 API 返回的 prompt_cache_hit_tokens / prompt_cache_miss_tokens（模型返回，非 agent 估算）

阶段预期命中率原因
首次对话60-80%system + tools 前缀命中（预热），对话内容 miss
第二轮起85-99%前缀 + 之前所有消息命中，只 miss 最后一轮
compaction 后70-85%system + tools 仍命中，Summary 是新的 miss
skill 切换后50-70%identity + rules 命中，从 tools/persona 开始 miss

前端底部状态栏实时显示「缓存命中 XX%」

设计原则总结

  • 固定在前，动态在后 — system prompt 5 层排序，固定内容最大化前缀缓存
  • Append-only — 所有动态内容追加在尾部，不插入中间，不修改已有
  • 压缩时重排 — 压缩是唯一重排窗口，Summary 放头部，最近消息在尾部
  • 不与部署端耦合 — 不猜分词器和 block 大小，trust the API 内部 block matching
  • 预热建缓存 — 启动时发最小请求，提前建立 system + tools 前缀缓存
